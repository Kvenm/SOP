# 2026-07-16 类目精度与多页候选优化

## 用户问题

1. 大类目不准确，小类目结果相对可用。
2. 商品数量约停在 40-50 个，希望允许更慢但采集更多候选。

## 根因

- 服务层 `MAX_ITEMS_PER_QUERY` 与 RPA 输入均硬限制为 50，导致分页函数存在但收满 50 条后立即停止。
- RPA 默认最多 3 页、硬上限 8 页，且分页按钮在整页范围模糊查找，存在误点其它箭头或重复页风险。
- `女装、男装、内衣` 等 1688 首页组合一级入口被用于推断商品类目；一级点击允许包含匹配，可能命中包含整组文本的祖先容器。
- 列表采集默认超时 180 秒，不适合 human pacing 下的多页采集。

## 实现

### 类目

- 一级导航使用直接文本/完整文本精确匹配；二级和叶子仍保留必要的受限别名匹配。
- 类目结果确认结合点击类目 ID、结果页类目 ID、结果 URL、标题和面包屑证据。
- 组合一级入口只保留为 `selected_category_path/navigation_category_path` 审计信息，不作为商品真实大类。
- 有商品结构化类目路径时继续优先导出真实路径；无商品级路径时只展示组合入口后的二级/叶子路径。

### 数量与分页

- 候选上限：50 -> 200。
- Web 默认候选扫描：120；默认目标可铺：60；两者分开配置。
- RPA 按候选数量估算分页，最多 12 页。
- 下一页查找限制到 pagination/pager/nav 区域，优先明确页码，再回退“下一页”。
- 翻页前后比较前 12 个商品 ID/链接指纹；列表未变化时返回 `page_not_changed` 并停止。
- 分页返回 `requested_limit/max_pages/pages_visited/collected_count/stop_reason/page_meta`。
- 列表采集默认超时提高到 600 秒；详情核验仍保持独立 180 秒默认。

## 验证

通过：

```text
git diff --check
Python py_compile
node --check rpa_collect.mjs
node --check rpa_detail.mjs
tag_collect smoke tests passed (61 tests)
```

新增回归覆盖：

- 默认候选 120、目标 60。
- 候选硬上限 200、目标硬上限 100。
- 组合一级不作为商品真实大类。
- Web 候选预算与目标可铺数分离。
- 一级严格匹配、类目 ID 确认。
- 动态页数、分页容器限定、页码优先、商品指纹和停止原因。
- 分页元数据从 RPA 透传到服务结果和导出配置。

## 未验证与残余风险

- 本轮未运行真实 1688 页面采集，无法证明当前页面 DOM 上每个类目和分页控件都稳定命中。
- 真实验收应先用单一叶子类目、候选 80-120 做低频测试；遇到登录、滑块、验证码或访问拒绝立即停止。
- 多页采集会显著延长任务时间；候选 200 不等于最终可铺 200，仍会经过类目、筛选、历史排除和详情核验。

## 防止“看似解决、实际没解决”的方法

1. 红色老问题不能引用旧运行记录中的“已完成”作为证据，必须重新找到当前可执行路径。
2. 每个截图反馈都要落成一个可失败的契约：负例优先，例如“出现代发价不能判定一件代发”“8 元不能通过 1-5 元”。
3. 区分三层证据：
   - UI 存在：只证明入口显示。
   - 本地回归通过：证明逻辑契约。
   - 真实 1688 低频验收：才证明当前账号/页面版本可用。
4. 详情筛选使用 fail-closed：缺少证据不能留在主结果，进入异常复核；不能把 `pending_detail` 当成命中。
5. 多步骤任务使用部分完成语义：已有可信结果先落盘，再记录失败子任务；零结果才整体失败。
6. 浏览器 UI 注入使用独立 Shadow DOM 与 `data-sop-*` 标记，避免状态文字污染商品、类目和安全验证文本判断。
7. 涉及滚动时记录“容器滚动”和“页面滚动”两组证据；类目菜单交互不得以 body 滚动为前提。
8. 滑块验收只观察自然触发，不主动制造、不代替用户操作、不绕过平台验证。

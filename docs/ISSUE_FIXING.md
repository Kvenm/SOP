# 问题修复与回归方法

本文件是 SOP 项目处理 Bug、截图反馈、问题汇总和“上次修过但仍复现”问题时的通用方法。日期运行记录用于保存一次任务的事实，本文件保存跨任务复用的规则。

方法来源案例：`docs/RUNS/2026-07-20-workbench-feedback-red-bug-fixes.md`。

## 适用范围

遇到以下任务时，改代码前必须先读本文件：

- 用户反馈功能错误、字段错误、交互错误或导出错误。
- 用户提供截图、录屏、问题汇总文档或复测结果。
- 旧问题被重新标红、再次出现或用户认为没有真正解决。
- 多步骤任务存在部分成功、部分失败、暂停或恢复问题。
- 修复依赖真实网站、浏览器、账号、第三方接口或外部运行环境。

## 开始修复前

1. 把用户反馈逐条列成问题清单，不遗漏截图标注、颜色和补充说明。
2. 标明新问题、重开问题和关联问题。重开问题一律恢复为 `open`，不能引用旧记录中的“已完成”作为当前结论。
3. 明确目标、非目标、允许修改文件、禁止修改文件和验收命令。
4. 找到当前实际执行路径、数据来源和用户看到结果的最终出口。代码中存在入口或函数，不等于用户路径已经生效。
5. 能安全复现时先复现；不能复现时记录缺少的真实环境证据，不用猜测补结论。

建议使用以下问题表：

| 字段 | 内容 |
|---|---|
| 问题 | 用户实际看到的错误 |
| 状态 | 新问题 / 重开问题 / 关联问题 |
| 当前路径 | 用户操作到错误结果经过的真实代码和数据链路 |
| 根因 | 导致错误的最小可解释原因 |
| 修复 | 代码、规则或交互调整 |
| 负例回归 | 修复前会失败、修复后应通过的案例 |
| 环境验收 | 本地、浏览器、服务器或真实第三方环境证据 |
| 残余风险 | 尚未得到真实证据的部分 |

## 根因与证据规则

问题结论至少区分以下三层证据：

1. `UI/代码存在`：只能证明入口或实现存在。
2. `本地回归通过`：证明逻辑契约在可控输入下成立。
3. `真实环境验收`：证明当前账号、页面版本、服务器或第三方环境中的完整路径可用。

不能用第一层证据替代第二、第三层。真实环境没有验收时，应明确写“代码与回归已修，真实环境待验收”，不能直接写“彻底解决”。

排查根因时优先回答：

- 错误值最早在哪里产生？
- 中间哪一层把缺失、未知、失败或暂停误当成了成功？
- 用户最终看到的页面、表格或状态是否使用了另一条旧路径？
- 是否只修了入口显示，没有修服务端约束、最终导出或恢复流程？
- 是否存在数量上限、截断、超时、缓存或多任务共享状态等隐含条件？

## 修复原则

### 重开问题重新取证

- 不沿用旧“已解决”结论。
- 重新检查当前代码路径、当前版本和当前部署状态。
- 找出旧修复为什么没有覆盖用户实际路径，并把遗漏原因写入运行记录。

### 负例优先

每个 Bug 至少增加一个修复前能够失败的负例。例如：

- 出现相似文字不能误判为目标能力。
- 超出区间的数值不能通过筛选。
- 一个子任务失败不能清空已经成功的结果。
- 页面出现入口不能等价于后台执行成功。

只有正例会让“功能能运行”和“错误已修复”混为一谈。

### 关键条件 fail-closed

涉及资格、价格、运费、履约、风险、权限、数据真实性等关键条件时：

- 明确不满足：剔除或阻断。
- 缺少可靠证据：进入异常复核、待核验或失败状态。
- 禁止把 `unknown`、`pending`、字段缺失或解析失败当成通过。

### 多步骤任务保留部分成果

- 子任务独立记录成功和失败。
- 已有可信成功结果时先安全落盘，再返回部分完成状态和失败诊断。
- 零成功结果才整体失败。
- 暂停、取消、中断、失败和完成必须是不同状态，不能统一显示成“任务结束”。

### 系统性失败及时熔断

- 多个子任务依赖同一个入口、浏览器状态或外部服务时，连续出现相同前置步骤失败且仍为零成功结果，应停止剩余子任务。
- 熔断时记录连续失败次数、已尝试对象和跳过数量，并给出明确的恢复条件。
- 已有可信成功结果时仍遵守部分完成语义；不能为了熔断而丢失已完成成果。
- 禁止在入口失效、页面结构变化或账号受限时继续循环刷新、重复登录、重复调用第三方接口。

### UI、数据和控制信号隔离

- 注入第三方页面的状态 UI 应使用独立容器或 Shadow DOM，并带项目专用标记。
- 状态文字不得污染商品文本、类目文本、安全验证判断或字段提取。
- 滚动交互要分别记录页面滚动和局部容器滚动，不能依赖 body 滚动完成菜单操作。

### 同页近义字段按“短标签证据 + 语义隔离”提取

- 页面中出现相似词不等于同一指标。例如“月代销”“月代发订单”“近30天代发数量”必须分别映射，不能因为都包含“代发/月”而互相覆盖。
- 运费位置随商品模板变化时，不应依赖单一固定 selector，也不能从整页任意“运费”文本取值。应在主文档、开放 Shadow DOM 和各 frame 中收集短、可见、带明确标签的局部证据，再按最短候选优先解析。
- “退货包运费”“赠运费险”“运费查询”等权益/工具文字是负例；没有“运费/快递费/代发运费 + 金额（或首重）”的短证据时保持待核验。
- `<10`、`80+`、`100以内`、`1.8元起`属于区间或边界表达，原始符号必须保留。涉及最小/最大筛选时，只有整个可能区间都能证明满足条件才通过；下限值不能冒充确定金额。
- 字段级核验记录应保存短证据文本、来源位置类型和 selector 提示，方便下一次页面改版时判断是字段缺失、位置变化还是误取。

### 第三方插件字段要验证“激活标签页 + 异步就绪”

- 页面上人工可见的插件字段，不代表自动新建的后台标签页在同一时刻已经有该字段。浏览器扩展、采购助手和悬浮分析面板可能只在活动标签页中初始化，或在原生商品详情加载后继续异步请求数据。
- 真实批次若出现“原生详情字段稳定命中、插件字段全量缺失”，应先检查标签页是否置前、插件容器是否出现、字段值是否晚于 `DOMContentLoaded`，不能继续把问题归因于 Shadow DOM 或正则。
- RPA 读取这类字段时应先把目标详情标签页置前，再对明确的插件容器或短标签做有限轮询；每轮重新读取 DOM，达到时限后保持缺失/待核验，不能无限等待、刷新页面或猜值。
- 等待前后证据要合并，避免页面滚动、吸顶栏切换或插件重绘使已经出现的短标签在最终读取时消失。
- 负例至少覆盖：字段延迟出现后能命中；字段始终不出现时有限停止；数字运费与页面其它位置的“包邮”同时存在时，以发货区短标签证据为准，不能互相覆盖。

### 模态滚动问题按“真实滚动容器 + 滚动链”取证

- 不能只看 `body`；先用浏览器计算样式和 `scrollTop/scrollHeight/clientHeight` 找出真实滚动容器，例如工作台常见的是 `.workspace`。
- 打开模态时保存并锁定页面和背景容器位置，关闭后精确恢复；模态、内容区和局部列表设置 `overscroll-behavior`。
- 局部列表到达顶部/底部时，滚轮可能继续传给祖先。负例必须在列表边界继续滚动，断言背景 `window.scrollY` 和背景容器 `scrollTop` 都不变化。
- 重绘级联列表时不要使用单一 `preserveScroll` 布尔值。按受影响列保存：点击一级只保留一级，点击二级保留一级/二级，勾选叶子保留全部；真正更换数据源或搜索时才全部重置。

### 第三方虚拟列表必须“局部滚动后重新查找”

- 第三方菜单、虚拟列表或懒加载列表中，“当前 DOM 没找到目标”不等于完整列表没有目标；只在找到节点后才调用局部滚动，无法处理尚未渲染的下方项目。
- 使用有限循环：查询当前已渲染节点 -> 选择并滚动真实局部容器 -> 等待重绘 -> 重新查询。每轮都重新取 locator/节点，不能沿用滚动前的空结果或过期节点。
- 滚动候选必须来自菜单/列表自身及其祖先，排除 `body/html`；每轮记录容器、`scrollTop` 前后值、页面 `window.scrollY`、尝试次数和停止原因。
- 到达底部、没有剩余可滚容器或达到最大次数时必须停止，返回可见文本和滚动诊断；不能刷新页面、无限循环或降级到宽泛搜索。
- 负例至少覆盖：目标在初始可视区下方但滚动后出现；目标不存在时有限停止；两种情况下背景页面滚动位置都不变化。

### 多级悬浮菜单不能沿用普通筛选的长等待节奏

- 一级、二级、叶子类目属于同一次悬浮会话；若每层都复用普通筛选的数秒 `before/after click` 等待，第三方菜单可能在叶子点击前自动收起。
- “目标精确文本存在但尺寸为 0，菜单祖先为 `display:none`”应识别为菜单收起，不得解释成网站没有该类目。
- 菜单收起后允许在同一页面快速重新悬浮已确认的父级路径，再重新定位并点击叶子；每次恢复只执行一次，仍需保留真实鼠标交互和最终结果页确认。
- 未命中的点击动作应立即返回，不要继续空等弹窗超时，否则恢复动作开始时菜单早已关闭。
- 负例应让菜单在父级悬浮后自动超时关闭，断言系统能记录隐藏目标、重新展开父级、只点击一次叶子；真正不存在的目标仍按有限滚动失败处理。

### 文本命中不等于鼠标命中

- 多级菜单定位时必须区分“用于确认文字的节点”和“真实鼠标需要悬浮的交互节点”。二级/三级标题优先使用精确的 `a`、`button`、`role=button` 或标题节点；不能无条件取最近的巨大 `li`、分组或菜单容器。
- 诊断至少记录真实指针目标的标签、class、文本、宽高和坐标。日志只写“餐具 matched”不足以证明悬浮正确；如果目标元素尺寸远大于标题或中心落在空白区，应按交互目标错误重新取证。
- 父级恢复不能只检查每一步是否找到了文字。恢复完成后必须立即检查下一层目标是否获得非零尺寸；若父级显示 `matched` 但下一层仍隐藏，应返回 `reopen_not_visible` 等失败状态，不能记录恢复成功。
- 负例应覆盖“标题位于高 `li` 顶部、移动到 `li` 中心不会展开子菜单”的页面。断言鼠标落在精确标题上，并覆盖“父级均命中但下一层仍为零尺寸”的假成功场景。
- 元素存在宽高也不等于处于真实可交互区域。必须同时检查最近 `overflow:auto/scroll/hidden` 容器的裁剪边界；目标位于容器可视区外时先完成局部滚动并确认 `target_within_container=true`，否则不得开始鼠标动作。
- 第三方页面可能给滚动容器设置 `scroll-behavior:smooth`。写入 `scrollTop` 后立即读取可能仍是旧值，随后按旧坐标移动会关闭菜单。需要临时使用即时滚动、等待至少两个动画帧，再重新读取目标和容器几何位置。
- 从一级入口到右侧/下方级联菜单时，直线移动可能斜穿其它一级类目或页面内容。应保存上一层真实指针位置，先水平进入当前菜单容器，再沿容器内部移动到目标高度，最后移动到目标文字；诊断记录 `pointer_route` 和中间点。

### 长进程提醒必须走实时旁路

- 如果子进程会等待人工数分钟，不能等最终 stdout/返回值才提示。业务最终结果和实时控制信号要分开传输。
- Node/Python 场景可让 stdout 继续只输出最终 JSON，stderr 使用固定前缀输出逐行 JSON 进度；Python 并发读取两条管道，识别前缀后立即转发任务进度。
- 人工介入事件必须带稳定 `alert_key`；前端按 `task_id + alert_key` 去重，轮询同一状态不得重复播放声音或弹窗。
- 负例应让子进程先发进度、延迟一段时间再结束，断言回调发生在子进程结束之前，避免“有事件字段但仍是假实时”。

### 外部安全验证只做人工接管

- 遇到登录、滑块、验证码或平台风控时停止自动操作并提示人工处理。
- 可以在明确等待时限内轮询页面是否恢复。
- 不点击、不拖动、不破解、不刷新验证页，不主动制造验证场景。

## 验收要求

按风险从内到外验证：

1. 编译、语法和静态检查。
2. 定向负例回归。
3. 完整 smoke/单元/集成测试。
4. 页面桌面与窄屏交互、控制台错误检查。
5. 部署环境只读状态确认。
6. 必要时进行低频真实环境验收；涉及 1688 时继续遵守 `docs/RISKS.md` 和人工安全验证边界。

无法执行某一层时，收尾必须写清：未运行项目、原因、残余风险和下一次应观察的证据。

## 文档沉淀

重要问题修复应在 `docs/RUNS/` 保存：

- 原始问题清单以及新/旧状态。
- 用户证据和可复现路径。
- 根因、修复位置和负例测试。
- 本地、浏览器、服务器和真实环境各自的验证状态。
- 没有执行的测试和残余风险。
- 这次旧修复为什么失效，以及如何避免同类问题再次发生。

如果本次任务总结出了跨任务适用的新规则，应同步更新本文件，而不是只留在日期运行记录中。

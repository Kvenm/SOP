# 标签选品采集指南（tag_collect）

> 命令为只读/导出型；Web 工作台默认真实数据模式，通过 Playwright/RPA 打开 1688 页面采集和详情核验。开发样例模式必须显式开启，不能作为正式测试结果。

## CLI 调用

启动本地 Web 筛选测试工作台：

```bash
python3 {baseDir}/cli.py tag_collect --serve --port 8765
```

命令行采集并导出：

```bash
python3 {baseDir}/cli.py tag_collect --categories "家居日用品,收纳清洁" --tags "微信小店,一件代发,48小时发货" --sample-data
```

| 参数 | 默认 | 说明 |
|------|------|------|
| `--serve` | false | 启动本地 Web 筛选测试工作台 |
| `--host` | `127.0.0.1` | Web 监听地址 |
| `--port` | `8765` | Web 监听端口 |
| `--categories` | `""` | 复选类目标签，逗号分隔 |
| `--tags` | `""` | 复选运营标签，逗号分隔 |
| `--keywords` | `""` | 额外搜索词，逗号分隔；不传则由类目和搜索型标签生成 |
| `--source-urls` | `""` | 直接采集真实 1688 搜索页或商品详情页 URL；适合账号登录受阻时测试公开页面真实数据 |
| `--exclude-tags` | `""` | 排除标签；命中标题、类目、风险提示或标签来源时过滤，并写入任务快照 |
| `--max-queries` | `20` | 最大查询词数量 |
| `--max-items-per-query` | `120` | 每个查询词候选扫描预算上限，最多 200；数量越大、分页越多、耗时越长 |
| `--target-publishable-count` | `60` | 目标可铺商品数量，最多 100；与候选扫描预算独立 |
| `--output-format` | `xlsx` | 导出格式：`xlsx` 或 `csv` |
| `--collect-source` | `rpa` | 真实采集来源：`rpa` 打开真实 1688 页面；`api` 调用 AK 接口 |
| `--sample-data` | false | 开发样例模式，不调用 1688；正式测试不要开启 |

## Web 工作台使用

- 推荐入口：`python3 cli.py tag_collect --serve --port 8765`，再打开 `http://127.0.0.1:8765`。
- Web 将“候选扫描上限”和“目标可铺数”分开：工作台默认使用“深度 200”，目标可铺默认 60；也可一键切换“快速 50 / 标准 120 / 深度 200”。CLI 未显式传参时仍保持 120。真实采集会按目标动态估算分页，最多 12 页，使用慢速人类节奏；滑块默认等待人工处理并尝试续跑同一任务，超时或仍受限才停止。
- 分页结果会返回 `pagination_records`、`pagination_pages_visited`、`pagination_collected_count`；每页记录提取数、去重接收数、下一页方式和停止原因。分页点击后页面商品指纹没有变化时会停止，避免重复采集同一页。
- Windows 支持：页面“启动采集浏览器”会优先查找 `CHROME_BIN`、Google Chrome，再回退 Microsoft Edge，并仅在 `127.0.0.1` 启动 CDP。Windows 服务必须运行在已登录用户的交互桌面会话中，否则 Chrome、扫码、滑块和验证码窗口可能不可见。
- 远程 Windows 主机推荐仍以 `--host 127.0.0.1 --port 8765` 启动，再使用 `ssh -N -L 8765:127.0.0.1:8765 <host>` 转发工作台。不要绑定 `0.0.0.0`，也不要把 CDP `9222` 暴露到网络。
- Windows 启动环境应设置 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`，避免 Python 与 Node 之间的中文类目/筛选 JSON 被系统 GBK 编码破坏。
- Web 默认使用“单类目任务”：选择新的叶子类目会替换上一个类目，避免连续任务串入。需要一次采集多个类目时，必须显式勾选“多类目任务”。
- 多类目任务会继续按类目隔离执行，但所有类目共享“候选扫描上限”；120 个候选是整个任务的总预算，不会给每个类目重复分配 120 个。类目越多，每个类目的候选预算越少，建议优先按二级类目拆成小批次运行。
- 多类目独立任务重新进入首页时，类目菜单使用真实鼠标移动/点击展开。一级/二级/叶子使用短级联节奏；如果精确叶子已存在但菜单祖先变为隐藏，RPA 会在同一页面重新悬浮已确认的父级路径并重试一次，不把“菜单收起”误报为“网站无此类目”。若目标类目尚未由页面渲染，RPA 会对菜单局部容器执行有限的“分段滚动 -> 等待重绘 -> 重新查找”，默认最多 18 步，可用 `TAG_COLLECT_RPA_CATEGORY_SCROLL_STEPS` 调整（硬上限 30）；全过程不依赖整页滚动。失败会返回隐藏精确目标、恢复步骤、容器、`scrollTop`、尝试次数、停止原因和可见类目文本；若尚无任何成功结果且连续 2 个类目都失败，系统会停止剩余类目，避免反复刷新 1688 首页。
- 类目弹窗打开时同时锁定 `body` 和实际滚动容器 `.workspace`，并使用 `overscroll-behavior` 与非 passive wheel 边界保护阻止滚动链传到背景。点击一级保留一级栏位置，点击二级保留一级/二级栏位置，勾选三级保留三栏位置。
- 二级类目行右侧提供明确的“全选 N”按钮，三级栏顶部也提供“全选当前二级 N 项”，只写入其下三级叶子路径，不会把非叶子二级路径提交给后端。
- 月代发订单、代发运费、代发权益、发货时间和商家特色集中到页面前部的“重点筛选”；月代发与代发运费支持自定义最小/最大区间，进入详情核验后的后置筛选计划。
- 商家特色按 1688 页面限制为单选：不限、超级工厂、源头旗舰、实力商家。
- 一件代发、7天无理由退货、24H/48H 发货等入口已去重；旧模板中的卖家会员类型/卖家服务会被服务端清洗。
- 筛选模板使用独立的可见操作区，存储在 `{TAG_COLLECT_DATA_DIR}/filter_templates.json`，支持保存、加载和删除，并显示已保存数量/保存结果。
- Web 采集通过 `/api/task/start`、`/api/task/status`、`/api/task/cancel` 后台执行；顶部固定任务卡显示阶段、百分比、页数/候选数并直接提供停止按钮。完成时显示 `collection_stop_reason` 和短缺原因，并明确“任务已结束，不会停一会再自动继续”。停止会向 Python 服务和 Node RPA 传递取消事件并终止当前 RPA 子进程；刷新页面时会恢复同一服务进程内仍在运行的任务。
- 页面默认关闭“开发样例”，即默认采集真实 1688 页面数据。若弹出登录或验证页面，用户需要在浏览器中扫码/处理验证。
- 标签不会全部拼成搜索词。`一件代发`、`48小时发货`、`7天包退货/七天无理由`、`批发包邮`、`实力商家` 等会进入 `native_filters`，由 RPA 在 1688 搜索页尝试点击/勾选。
- 截图框出的搜索页服务筛选已接入 `native_filters`：`严选`、`分销严选`、`一件代发`、`退货包运费`、`7天无理由退货`、`24H发货`、`48H发货`、`官方物流`、`密文面单`、`晚揽必赔`、`24H支揽率`、`48H支揽率`、`合并供应商`。同义筛选会按 key 合并别名并保留执行记录。
- `所在地`、`商家特色`、`经营模式` 属于下拉筛选，RPA 会先尝试展开筛选组再点击选项；执行结果仍以 `clicked/not_found/click_failed` 为准。`店铺商品数` 当前为预留字段，不会伪造成已过滤结果。
- 截图中的 `商品星级`、`好评率`、`评价数`、`评价标签` 属于详情评价块字段。系统会先保留候选，进入详情页核验后再重评估筛选；新增导出字段为 `5.10 商品星级`、`5.11 评价标签`。
- 详情核验后未满足星级、好评率、评价数或评价标签筛选的商品，会从内部可信主结果移入 `filter_excluded_rows`；XLSX 展示层按用户 7.21 模板要求仍会把它汇总到唯一主表，自动化判断必须读取 JSON 分类。
- 如果当前类目或页面没有某个原生筛选项，系统会记录 `not_found` 并在 Web 和 JSON 快照中提示，不能把它当作已筛选成功。
- 好评率、品退率、发货率、评论数、复购率、近30天销量、代发订单量支持区间标签；页面读不到的字段保持待详情页核验或人工复核，不猜值。
- 类目区支持一级/二级/三级路径。当前 `category_dict.json` 是本地种子字典，状态为 `partial_seed_needs_official_sync`，后续仍需采集/确认完整官方 1688 类目字典。
- `女装、男装、内衣`、`日用餐厨、居家日用` 等一级名称是 1688 首页的组合导航组，不是商品真实大类。RPA 对第一级只允许精确文本命中；导出只有拿到商品级类目路径时才展示真实完整大类，否则只展示组合入口之后的二级/叶子路径，并在审计字段保留完整导航路径。
- 商品类目使用三态门禁：`matched`（已匹配）、`mismatched`（结构化证据确认错类目）、`unknown`（商品级证据不足或 ID/路径证据冲突）。数字 ID 不同但路径一致时按路径确认；只有 ID 冲突且缺少路径时保持 `unknown`，不会直接永久拒绝。标题只允许正向辅助，标题未命中不能直接判错。
- `unknown` 不进入主 `rows/top_items/publishable_count`，不会写入历史拒绝池；它会保留在 `category_unknown_rows` 并进入详情核验队列。详情证据确认后可迁入主结果或筛除区。
- unknown 完成一次成功详情读取后若仍无类目证据，会停止自动重复访问并留给人工复核；登录、滑块或验证码导致的失败仍允许人工处理后重试。
- 如果账号登录不上或一直触发校验，可以在“1688 页面 URL”粘贴浏览器里能打开的搜索页/商品详情页链接。URL 模式仍然读取真实页面，不会使用样例数据；但公开页面看不到的运费、品退率、发货率等字段仍会保持待核验或失败。
- 如果出现滑块/验证码，可视浏览器默认等待人工最多 5 分钟；人工完成后继续同一 RPA 子任务。系统只轮询页面是否恢复，不刷新、不点击、不拖动、不破解验证。超时或仍受限才返回 `security_verification_required`；已有成功类目的结果可按部分完成规则导出。
- 工作台默认开启声音提醒并保存在当前浏览器：登录、滑块或验证码出现时播放双短音，任务完成时播放完成音；关闭开关后不播放。Node 通过 `SOP_RPA_PROGRESS` stderr 行实时上报 `manual_intervention`，Python 转发到后台任务进度，前端按任务 ID 和 `alert_key` 去重。
- 在真实 Chrome CDP 模式下，登录页或安全验证页会保留在采集 Chrome 中，后台任务显示“等待人工处理”而不是“执行失败”。人工完成验证并确认搜索页恢复正常后，回到工作台重新点击“开始自动采集”；页面不会展示带临时令牌的完整 punish URL。
- 风控较敏感时，推荐采用“人工浏览 + 系统读取已加载页面/候选 URL”的低风险模式：先由人工在 1688 页面勾选原生筛选并浏览候选商品，再把候选 URL 或已加载页面交给系统做去重、评分、详情核验和导出。不要使用代理池、验证码绕过、反爬逆向或高频自动重试。
- RPA 默认使用 `TAG_COLLECT_RPA_PACING=human` 慢速节奏：页面加载、筛选点击、滚动、详情核验都会加入随机等待和分段滚动。Web 默认显示深度 200、目标可铺 60，候选和自动详情核验上限最多 200；CLI 默认候选仍是 120。真实账号首次验收建议先切到“快速 50”或手动调低核验量，确认登录和页面稳定后再逐步提高。仅开发排查时可临时设为 `TAG_COLLECT_RPA_PACING=fast`。
- Web 工作台默认开启“详情补字段/自动核验”，采集列表后会按上限进入详情页补充代发价、月代发订单、月代销/近30天件数、运费、品退率、发货率等关键字段；默认上限 200。选择一件代发、运费区间等详情筛选后，未核实或未命中的商品不会留在内部可信主结果，会进入 JSON 的 `filter_excluded_rows`。
- 详情页的“月代销”只映射到 `units_30d/近30天件数`；“月代发订单”和“近30天代发数量”是不同指标，不得互相覆盖。`<10`、`80+`、`100以内`等原始边界文本会保留。
- CDP 详情核验会先把新建商品标签页置前，并对采购助手 `.goods-operation-panel-media` 等短标签做有限异步等待；默认最多 12 秒，可用 `TAG_COLLECT_RPA_DETAIL_EVIDENCE_WAIT_MS` 调整，硬上限 30 秒。等待前后的证据会合并；达到时限仍没有月代销时保持待核验，不刷新页面、不猜值。
- 运费不依赖固定页面位置：RPA 会从主文档、开放 Shadow DOM 和 frame 中优先读取类似“运费￥10起/运费￥1.8起”的短可见标签，再使用整页文本兜底；“退货包运费、赠运费险、运费查询”不作为金额证据。`1.8元起`只证明下限为1.8元，配置运费上限时若无法证明完整区间满足条件，会进入待复核而不是假装通过。
- 数字运费短标签优先于页面其它区域的“一件包邮”文案；只有发货模块本身明确显示包邮/免运费且没有数字运费时，代发运费才写“包邮”，并与“是否包邮”保持一致。
- 运费、月代销和月代发订单的 JSON 字段级核验记录会附带 `evidence_kind/evidence_text/evidence_source/evidence_selector_hint`，用于审计实际命中的短标签。
- 类目选择是模态弹窗，包含“全部类目 / 收藏类目”、三栏选择、已选区和整二级全选；收藏仅保存在当前浏览器。单个叶子导出文件名使用完整类目，全选同一二级全部叶子时使用二级类目名，其它多类目使用首类目加“等N类目”，并保留 run_id 防覆盖。
- 多类目子任务独立执行；单个类目失败但已有成功商品时，结果返回 `collection_status=partial`、`partial_failures` 并继续生成导出。没有任何成功商品时仍按原错误阻断。
- Web 的“目标可铺数”对应 `target_publishable_count`，按系统规则预判的 `可铺` 数量计入达标；`谨慎` 只作为可观察候选，不计入满足投放数量。
- 系统会记录本地历史筛除池 `{TAG_COLLECT_DATA_DIR}/rejected_products.json`。同一筛选签名下，列表硬筛失败、排除标签命中、详情后筛选失败或详情后明确“不建议”的商品，下次采集会先跳过，减少重复详情核验和重复人工判断。
- 类目拒绝池只持久化 `mismatched`；`unknown` 代表证据不足，禁止持久化为错类目。
- 详情核验后会重新计算推荐分、推荐等级和微信小店建议，并写入 JSON 的 `rescore_records`；JSON 同时保存目标可铺数、候选扫描、历史跳过和短缺原因。
- 采集结果会返回 `automation_state`，用于区分接口成功和业务流程状态：
  - `pending_detail`：列表初筛完成，但仍有高潜商品待详情页核验。
  - `paused`：列表采集成功，但详情页遇到登录、滑块、验证码或访问拒绝，已停止后续详情核验，需要人工接管。
  - `partial` / `failed`：详情字段未完整可信，导出后重点复核异常/边界商品。
  - `verified` / `sample_verified`：详情字段已完成本轮核验；其中 `sample_verified` 只代表样例流程通过。
- JSON 快照会写入任务状态、当前阶段、建议动作、详情核验暂停原因、已核验/失败/待核验数量，避免把“列表成功”误读成“详情字段都可信”。
- 样例详情核验会把 JSON 行状态更新为 `sample_verified`，并生成字段级核验记录。`sample_verified` 只代表流程和字段映射已通过样例验证，不代表真实 1688 数据可信；真实性提示不占用 24 列主表。
- 只有能证明来自真实页面采集或真实详情页核验的行，JSON 才允许标记 `数据模式=真实数据`；旧批次、手工拼入或来源字段缺失的行会标记 `来源未知/需核验`，不能直接用于选品和铺货。
- `partial_verified` 表示真实详情页只提取到部分字段；未提取到的运费、品退率、发货率等字段必须人工复核。
- 如果通过 `--host 0.0.0.0` 让其他设备访问页面，真实采集仍会被服务端禁用并锁定为远程只读/样例模式；当前不是多人真实采集服务。
- Web 第一版不是绕过 1688 风控的爬虫，不做验证码绕过、反爬规避或高频页面抓取。
- 每次新采集会先清空旧任务结果再发起请求；三个采集入口有统一并发保护，旧任务响应不会覆盖新任务。

展示时先输出 `markdown` 字段，再补充面向用户的下一步建议。不要把导出表当作已核验铺货清单。

## 字段编号

字段编号采用“分组编号.组内序号”：

- `1.1`：第 1 组的第 1 个字段，如“序号”
- `1.2`：第 1 组的第 2 个字段，如“商品类目”

该编号用于字段确认和验收沟通，不是小数、优先级或版本号。用户说“保留 1.1/1.2、调整 2.4”时，Agent 应按字段编号理解并追踪到对应导出列。

## 人工复核规则

导出后仍在 JSON 保留人工复核审计信息，但不占用 `选品结果` 24 列主表。复核重点是 `谨慎`、字段缺失、风控暂停、品牌/IP 不确定和规则冲突商品；系统已明确不满足筛选的商品会进入历史筛除池。Agent 应提醒用户在 JSON 中更新：

- `人工复核状态`
- `人工复核备注`
- `微信小店铺货建议`

列表字段只做初筛。运费、是否包邮、是否一件代发、品退率、发货率、24 小时揽收率、发货时效、起批量、SKU、供应商可靠性等关键字段，仍需进入详情页或可信来源核验后才能作为最终铺货依据。

## 导出工作表

`.xlsx` 严格只包含一个 `选品结果` 工作表，固定为用户 7.21 模板确认的 24 列：序号、商品类目、商品主图、商品标题、商品ID、商品链接、月代发订单、是否一件代发、近30天订单数、近30天件数、近30天销售额、代发价、上架时间、评论数、库存、代发运费、命中标签、是否包邮、好评率、好评率区间、48小时揽收率、发货时效、发货率区间、采集时间。

导出展示层按 `rows -> category_unknown_rows -> filter_excluded_rows` 顺序合并，优先按商品 ID、其次 URL 去重并重排序号。字段级核验记录、原生筛选执行记录、真实性、异常原因和人工复核状态全部保存在同批次 JSON，不再创建 Excel 附表。

## 异常处理

| 场景 | 表现 | Agent 应对 |
|------|------|-----------|
| Web 端口被占用 | 启动失败或无法监听 | 换一个端口，例如 `--port 8766` |
| 未安装 Playwright | `未安装 playwright` | 执行 `npm install` 和 `npm run install-browsers` |
| RPA 弹出登录页 | 浏览器停在登录/验证页或返回 `login_required` | 用户扫码登录或处理验证；如果账号登录不上，先粘贴浏览器里能打开的 1688 URL 测试公开页面真实数据 |
| 一直触发安全校验/滑块验证或访问被拒绝 | 状态栏显示等待人工；默认等待最多 5 分钟，人工完成后同任务续跑；超时返回 `security_verification_required`、`action=manual_handoff` | 在当前真实 Chrome 页签人工完成验证；系统不会绕过、点击或拖动验证。达到等待时限后可处理好页面再重跑失败部分，已有成功类目导出不丢失 |
| 列表成功但详情页触发风控 | `automation_state.status=paused`，`verification_stopped_reason` 有值，JSON 写入暂停原因 | 说明“列表初筛成功，但详情字段未完整可信”；不要直接铺货，等待人工处理验证后再继续详情核验 |
| API 真实采集无 AK | `AK 未配置` | 引导用户先 `configure`，或改用默认 RPA 真实页面采集 |
| 导出后字段未核验 | `verification_status: unverified` 或字段为“待详情页核验” | 明确这是初筛结果，不能直接进入正式铺货结论 |
| 原生筛选项找不到 | `filter_results.status: not_found` | 告知用户当前类目/页面没有展示该筛选项，不能当成筛选成功；必要时换类目或手动打开 1688 页面确认 |
| 样例详情核验完成 | `verification_status: sample_verified` | 明确这是样例核验结果，不是真实 1688 详情页核验 |
| 真实采集限流/授权异常 | HTTP 401/429 等 | 按 `references/common/error-handling.md` 处理 |
